# PaperBridge module boundaries

## Browser workspace

`src/App.tsx` owns session state and composes the one-field research-focus form, paper results, free comparison, local gap-lead panel, optional AI gap hypotheses, evidence inspector and experiment plan. `src/lib/api.ts` calls only same-origin `/api` routes. Browser modules never read provider credentials or import backend modules.

`src/components/BriefForm.tsx` renders only `Brief.field` and the question. `ResourcesPanel.tsx` edits the root-owned optional resource notes in a dedicated tab before hypotheses. `shared/research-query.ts` turns the field and question into editable discovery terms by simple keyword filtering. **Find papers for this focus** populates the search input and starts discovery; this is not a model interpretation of the question. Field/question edits clear old AI analysis. No second field is required.

`src/components/PaperPanel.tsx` shows source provenance, free-copy links, grouped versions, coverage and per-collection status. `shared/paper-filters.ts` owns pure filtering. The default discovery view admits all free-linked topic matches. The explicit **Ready for full-text analysis** filter requires a `fullText` provenance object, at least one nonempty `kind: 'full-text'` passage, `Full text retrieved` coverage and no reported truncation. A free link, identifier, metadata object or coverage string alone cannot admit a record. The internal `verified` filter name means imported text availability, never scientific verification or the complete publication package.

`src/App.tsx` automatically checks up to 12 supported search candidates, with two retrieval workers and visible progress. **Check more article texts** starts another bounded batch. Failed retrievals stay inspectable with explicit per-paper retries; no result is promoted to retrieved text merely because an import was attempted. Ready rows preview actual body paragraphs and **Read article body** selects a record and opens its reader. Selected records persist across searches.

Availability filters separately offer supported routes without a retrieval guarantee, or all source-reported free-copy records. Labelled excerpts require an explicit opt-in in retrieved-text mode. Additional source, publication-year and identified-preprint/mixed-version filters apply to the retrieved records; unknown years do not satisfy an explicit year range. Excluding identified preprints does not verify peer review. None of these filters extends the collections or proves absence of relevant literature.

`src/components/ComparisonPanel.tsx` opens its reader automatically with one selected record, enabling side-by-side comparison with two or more and allowing up to six. Supported full-text retrieval starts when a source is selected; explicit sequential batch retrieval and per-paper retry remain available. The default view is **Article body — retrieved text**, never an automatic abstract fallback. Abstracts are available only through an explicit view choice. Each paper has loading, ready, waiting, unavailable or failed body status. `shared/comparison.ts` filters stored passages by text kind, source section or phrase. Methods and findings come from source headings, not inferred AI summaries. Missing sections stay missing. PDF and external-repository links remain separate from imported text. `src/components/comparison.css` owns the reader-specific layout and states.

## Free comparison overview and evidence inspector

`shared/comparison-overview.ts` builds a local overview from selected article-body passages, excluding reference/acknowledgment sections. It requires at least two selected records with body text; abstracts are never a fallback. Common terms come from normalized words/phrases present in two or more retrieved bodies; distinct textual emphases are terms seen in one of those bodies but not the others. This measures retrieved wording, not scientific agreement, equivalent methods, contradictions or absence in the complete publication.

`src/components/ComparisonOverview.tsx` displays two selected papers at a time, common terms, and Question/Method/Findings/Limitations excerpt cards. The pure helper retains a matrix internally; the browser shows one aspect at a time, using headings or explicit textual cues. Missing aspects are unavailable, not inferred summaries. Short previews retain paper/passage references and an explicit truncation indicator.

The overview’s source/inspect controls and `GapPanel`’s **Inspect evidence** action route a citation to the root-owned `EvidenceInspection` state. `src/components/EvidencePanel.tsx` resolves that citation against selected stored text and shows the complete supporting passage, provenance and source link without requiring an AI hypothesis. A quotation’s existence does not prove its scientific interpretation. `src/components/comparison-overview.css` owns overview layout; the reader retains its own styles.

## Search and grouping

`server/sources/combined.ts` runs three search adapters concurrently: OpenAlex, Europe PMC and arXiv. It performs up to two bounded provider-specific phrase variants per source, deduplicates all candidates, then applies shared question relevance instead of interleaving incompatible provider rankings. Records without a source-reported free-copy link are excluded from this combined discovery workflow. Successful results survive another provider's failure; per-source status makes the incomplete search visible. All-provider failure is an explicit error, not an empty successful search or a saved fallback.

- `server/openalex.ts` applies the open-access filter for combined search, reconstructs positional inverted abstracts and preserves OA location links, license metadata and identifiers. These links can include university repositories; there is no separate universal repository crawler.
- `server/sources/europepmc.ts` requests core JSON with an OA constraint and normalizes source metadata, abstracts, PMC identifiers and free-copy links. Quoted keyword clauses prevent form text from overriding the OA search constraint.
- `server/sources/arxiv.ts` parses the Atom feed, retains arXiv version identifiers and marks manuscript/preprint origin. A shared queue spaces requests according to the API guidance. An arXiv record does not establish peer review or publication status.

Grouping uses DOI, PMC identifier, arXiv identifier or an already-known source identity. Similar titles alone do not establish duplicate identity. Provenance and distinct free-copy links are retained. A canonical record supplies the displayed source text; grouping does not assert that manuscript and published versions have identical contents.

`server/sources/common.ts` supplies stable sentence passage IDs, safe link normalization and bounded response reading. Source text is always untrusted data.

## Source store and full-text retrieval

`server/app.ts` validates requests and binds selected IDs to the server-side source store. A browser cannot supply invented paper text or an arbitrary retrieval URL. The bounded source/analysis caches expire after one hour; no database or account system is involved. Search responses preserve already-retrieved body text. Concurrent imports of the same paper share a pending retrieval.

`server/sources/fulltext.ts` constructs supported retrieval URLs from validated PMC/arXiv identifiers. It imports PMC article-body paragraphs from XML and arXiv article-body paragraphs from HTML, checks response identity, and preserves the original abstract. It does not crawl arbitrary metadata links, bypass paywalls, or parse PDFs. Retrieval and response limits are explicit; a shortened result is labelled **Full text excerpt**.

Figures, tables, references and supplements are excluded from the extracted prose. Mathematical formatting may be lost. The coverage label **Full text retrieved** refers to the supported article-body extraction, not the complete publication package. Full-text metadata records the source URL, retrieval time, license information when supplied, scope note and truncation state. Unknown licensing is not converted into a reuse grant.

Abstract and article-body passage IDs include the canonical paper ID, text kind, content hash and source-order index. Full-text passages also carry their source section. Quotations are rendered from these stored passages, never from model-generated quote strings. Updating the retrieved evidence clears an older analysis rather than retaining conclusions against changed source text.

## Local within-field gap leads

`shared/gaps.ts` scans supplied stored passages locally for lexical signals of author-reported limitations, future work and unresolved questions. `src/components/GapPanel.tsx` explicitly controls the supplied evidence scope: **Retrieved article body only** is the default and filters out abstracts; **Include abstracts too — limited evidence** is opt-in. A blank field does not block the free scan, and **Find gap leads** always opens: with zero selected records it displays selection guidance instead of being disabled. If no readable body is available, body mode reports that no article-body scan ran and exposes supported selected-text retrieval rather than silently scanning abstracts.

A displayed lead contains an exact signal sentence, its complete supporting passage, paper/passage IDs, source link, section and body/abstract provenance. Its **Inspect evidence** action opens that stored passage in the shared inspector. A lead is an author-stated issue in that passage, not a verified research gap across the field.

Nonbackground leads are ordered before background issues; within that grouping, full-text leads are preferred to abstract-only leads. Introductory/background statements are explicitly flagged as potentially already addressed by the same paper, and their follow-up requires reading that paper’s results first. Keyword overlap with the one field and question changes ordering, not the scientific interpretation of the source. No scientific confidence or novelty score is produced. Some negative/resolved phrases and reference sections are excluded, but the scan is still a heuristic: it can miss implicit issues or other languages and can misread context or statements about older work. A question does not authorize invented gap claims.

The panel reports selected-source body coverage and the chosen evidence scope. Abstract-only leads appear only after explicit inclusion and remain labelled. A completed scan with no explicit signals has an insufficient-evidence outcome; a body scan that could not run due to missing body text is distinguished from that result. It recomputes when the field, question or source passages change, including when body text finishes loading. A lead's visible **Search for follow-up work** terms route through combined discovery, so later research can be checked before a user treats it as a gap. A study limitation is not automatically a field-wide gap, and an empty search does not establish novelty.

## Optional model analysis and evidence validation

`server/analysis.ts` optionally develops at most two within-field gap hypotheses using the official OpenAI SDK, only when both the spending-enablement flag and a server credential are present. The field and question are data, not directions to manufacture a gap. The model contract separates source-supported evidence summary, a cautious gap rationale and a proposed approach; a missing discussion or author-stated issue does not itself prove a field-wide gap. It sends untrusted paper/form strings as data and instructs the model not to obey embedded directions. No tools execute model instructions. This reduces prompt-injection risk but does not guarantee model obedience.

Model input is bounded per selected paper and explicitly described as an excerpt. Validation uses the actual submitted `modelSources` subset, so a reference to a stored passage omitted from that excerpt is rejected. A reader may have more stored text than was submitted for AI analysis; omitted passages were not analyzed. Missing credentials never prevent paper search or free source comparison. Model failures do not load the saved example.

`shared/analysis-schema.ts` defines the structured response. `server/evidence-validation.ts` rejects invalid schemas, inconsistent insufficient-evidence outcomes, nonexistent paper/passage IDs, duplicate hypotheses and resource terms absent from cited text. An AI gap hypothesis needs at least two distinct selected source papers. These are provenance checks, not scientific verification or proof that a passage entails an interpretation.

An accepted analysis returns the stored source version from which its submitted passages were drawn; the reader may include additional stored passages that were not submitted to the model. `shared/evidence.ts` resolves citations against that snapshot. The evidence UI distinguishes source statements, PaperBridge interpretations and untested hypotheses, including whether a quotation came from an abstract or article-body text.

## Prior work, resources and examples

`server/prior-work.ts` runs two visible within-field queries through the same combined free-paper search: field plus research question, and field plus proposed hypothesis title. Free local leads have their own explicit follow-up search action; neither path requires a second field. Failed queries or partial provider availability produce **Search incomplete**, even when candidates exist. Results are related candidates for human inspection; no match never establishes novelty and no numerical novelty score is calculated.

`shared/resources.ts` conservatively compares explicitly cited method phrases with the user's resource notes. The UI tracks a revision, so editing and undoing an edit still invalidates an old assessment. Experiment plans warn when resources change after generation. Unknown quantities, timing or equivalent terms remain unresolved rather than becoming invented requirements.

`server/examples/` contains real retrieved records and a manually prepared, abstract-based **within-field network-ecology** example labelled `saved-example`. Its sensitivity comparison is an untested hypothesis motivated by selected sources, not an established gap, AI result or novelty claim. The example opens through an explicit separate-tab action. It is distinguishable from live results and is never a fallback for failed live requests. Synthetic paper fixtures are confined to automated tests.

## Runtime and access

The backend binds to loopback, limits JSON size and request frequency, rejects unrelated origins and does not enable CORS. Vite preserves the website Host header when proxying development requests. `server/config.ts` derives an exact Codespaces website hostname from runtime metadata; it does not disable hostname checks or allow a wildcard. The API's same-origin guard also recognizes that exact HTTPS website origin.

`npm run dev` starts website port 5173 and backend port 3001. In development, the backend root redirects to the known Codespaces website, or displays an explanation of the correct port. `npm start` serves a previously built website and API together on port 3001. This remains a team prototype, not a deployed public service with production accounts, durable storage or abuse controls.

## Connected discovery and manual prior work

`shared/discovery.ts` uses cached source sentences to extract exact citation-backed profile fields and conservative lexical finding tensions. Opposing directional outcomes require matching metrics, explicit finding cues, and shared domain terms. Scope-difference labels and per-source contexts do not establish scientific contradiction. `src/components/DiscoveryPanel.tsx` renders source/lead/context nodes, coverage, quotations and manual draft/optional AI actions. No discovery scan calls a model.

`shared/focus-guide.ts` and `BriefForm.tsx` compose user-applied question templates. `App.tsx` holds selected lead context separately from evidence inspection and draft state. Optional `/api/analyze` lead citations are validated against selected cached papers before model use. `server/analysis.ts` prioritizes referenced lead passages within the existing per-paper excerpt budget and treats all lead strings as untrusted data; response citation validation remains unchanged.

`POST /api/prior-work/search` accepts bounded question/optional field strings and uses existing combined literature search through `checkManualPriorWork`. `PriorWorkCheck.tsx` owns an explicit editable search and invalidates results on context/query edits. Opening tabs, leads or plans does not trigger retrieval or paid generation. `shared/experiment-plan.ts` stores original source citations/resources/focus plus editable question, data, methods, baseline, metrics, support/rejection criteria, variables, confounders and constraints. Unknown new fields remain blank, and edits/export are preserved.

## Purpose-focused workflow composition

`App.tsx` retains root session state and existing research modules under Focus → Papers → Find gaps → Experiment. Papers has Search & select / Read & compare. Find gaps has exactly Gap findings / Visual map and always enters on readable findings. Hidden mounted panels preserve reader/map state. Resources and generation are contextual disclosures inside findings; `ConnectionPanel.generationOnly` reuses readiness/spending controls without rendering another hypotheses dashboard. `ResourcesPanel.embedded` retains controlled inputs and replaces obsolete navigation copy.

`shared/gap-findings.ts` adapts existing `GapLead` and analysis records into one canonical view model. Author IDs are unchanged; AI IDs are namespaced by analysis/hypothesis ID. Known statements are excerpts from stored source text, not invented scientific conclusions. Generic, stale or background-only author issues are flagged insufficient. Derived titles trim only boilerplate prefixes; unresolved statements, source text and citations remain authoritative. Source-context citations are shared by both views.

`GapFindings.tsx` renders candidate selection and one selected explanation with one contextual next action, expandable passages, uncertainty and related work. `GapVisualMap.tsx` receives the same selected finding and references; it derives no alternate gaps or topics. It renders only relevant cited-source branches, an appropriately labelled relationship/interpretation and the unresolved issue around the focal question. Branch and drawer changes are local display state: no navigation, searches or model calls. Opening the inspector does not clear findings, hypotheses or edited drafts.

The original PNG assets are unchanged. The header restores the original icon/navy/violet identity; sans typography uses the existing self-hosted IBM Plex Sans family. Reduced framing and shared spacing/color tokens remain. Legacy topic-map utilities remain tested internally but no longer drive the gap workspace. Planning resources remain root controlled and generation costs retain known/unknown distinctions.

## Question relevance and query diagnostics

`shared/research-query.ts` exposes editable concept groups and two phrase-preserving query variants. A small explicit related-term vocabulary helps common synonym cases; it is not a semantic model. PMC and arXiv receive their documented quoted AND syntax; OpenAlex uses plain search text. `shared/search-relevance.ts` classifies and orders all deduplicated candidates consistently from titles and abstracts, with exact supporting text and missing-concept explanations. No abstract means no direct-match claim. Original research questions remain separate from editable query concepts.

`server/sources/combined.ts` caches successful bounded searches for ten minutes, shares in-flight identical searches and stops a provider's variants after failure/rate limiting. Other providers survive partial failure. `SearchResult` carries interpreted concepts and actual compiled queries. Even all-provider failures return safe search diagnostics through `AppError.searchDetails`; credentials and request URLs with secrets are never included. Search options are validated at the API boundary. Previously imported body text is retained in the paper store while question-specific relevance is refreshed.

Semantic Scholar remains unconfigured: its official docs were blocked (403) and no key/access was available. No endpoint/authentication guesses, scraping, new accounts or paid reranking were added.

## Required existing-research check before hypotheses

`shared/gap-check.ts` defines a chosen gap independently from the original research focus: its stable ID, question, rationale and source citations. `POST /api/gap-check` accepts `{brief, paperIds, gap}`. `server/gap-check.ts` derives at most two bounded queries from that chosen question and field, then reuses `server/prior-work.ts` and the combined literature search. This searches the available collections beyond the selected source set. Up to eight deduplicated candidates are retained, including abstracts and metadata; imported body text is not a prerequisite. Actual query outcomes and collection statuses stay visible, including partial failures.

The optional model assessment uses the existing server-side OpenAI SDK, configured model, credentials and explicit spending gate. It submits at most eight candidates and 12,000 characters of retrieved passages per candidate, with a 5,000-output-token cap and no SDK retries. These are request bounds, not a fixed price or account spending limit. Reported SDK usage feeds the existing cost estimate, including usage consumed by output that fails validation. Missing credentials or disabled spending leave the app and search usable, expose the retrieved candidates for manual inspection, and mark the AI assessment unfinished. Empty searches never incur an assessment call: only a completed empty search receives `assessmentNotNeeded`; failed empty searches remain incomplete.

Assessment output names only actual candidate/passage IDs. Every non-unclear judgment, including a materially different question, requires a valid retrieved passage. Metadata alone cannot establish an answer or a different investigated question. Quotations are rendered from stored candidate text, not supplied by the model. Abstracts and bounded body excerpts remain partial evidence; validating IDs does not validate scientific interpretation. Search/provider failure, an unclear candidate assessment, invalid output or model failure cannot become a no-match conclusion. The four outcomes distinguish potentially answering research, partial answers, no close match within completed searches, and incomplete/inconclusive checks. None establishes novelty.

`POST /api/gap-check/:id/review` accepts the same `{brief, paperIds, gap}` plus `decision: 'continue' | 'replication' | 'extension'`. The server requires a complete assessment (or genuinely empty completed search), then records the user's explicit review. Potentially answering work permits only an explicit replication or extension; continuing as an untouched gap is rejected. Client-supplied assessment text is never authoritative.

`POST /api/analyze` additionally requires the checked `gap` and `checkId`. The in-memory, bounded check store retains at most 100 checks for one hour. Both review and generation independently compare the normalized gap ID/question/rationale/citations, original research question and field, and sorted selected-paper IDs. A SHA-256 digest also binds the selected stored passage content: importing or changing text invalidates an earlier approval. Expired, lost, unreviewed or mismatched checks fail before hypothesis generation. Resource notes are deliberately excluded from this literature-check identity; changing planning constraints does not repeat a literature search, while existing plan/resource revision warnings still apply.

`server/analysis.ts` receives the canonical stored gap and reviewed assessment as server-owned context. Existing or partially answering work must constrain the hypothesis; a replication/extension decision must be labelled accordingly. Hypothesis evidence and method requirements still cite the selected stored sources through the existing validator. Checking a gap and generating a hypothesis are separate explicit requests and may each incur model costs when enabled; opening findings, evidence or map nodes does not trigger them.

Current limits: checks are session-server memory, disappear after a server restart, and are not a durable literature review. Retrieval remains limited to the configured free-paper collections and bounded results. No universal repository crawler, paywall bypass, exhaustive novelty claim, or automatic scientific entailment verification is provided. The manual candidate view cannot stand in for an unfinished AI assessment to unlock generation. Synthetic test assessors are injected only by automated tests; there is no production bypass switch.

Research-check outcome aggregation distinguishes uncertainty about an individual candidate from failed search coverage. After successful searches and citation-validated AI assessment, a supported whole/partial answer remains reviewable even if other candidates are inconclusive. Their uncertainties are retained; they are never treated as proof of an open gap. All-unclear evidence or any failed search remains incomplete. Aggregate status summaries are deterministic, with field-wide novelty/unaddressed claims excluded. Source-led gap extraction selects a concrete signal within the original passage before a generic introductory limitation notice; stored quotation text is never rewritten.

Recovery uses per-candidate strict validation: unknown, missing, duplicated or invalid citation claims are rejected and represented by an actual candidate ID with an explicit unclear/no-evidence row. Valid neighboring claims survive; no rejected reference is accepted. Overall malformed output still fails. `POST /api/gap-check/:id/reassess` checks stored identity/digest/expiry, revokes review before awaiting the SDK, locks concurrent review/generation/reassessment and reuses candidate snapshots without provider search. No automatic model retry is enabled, and the existing spending flag/usage costs apply.

Limited-coverage eligibility is server-derived from completed AI assessment, a valid cited whole/partial answer and actual successful/failed collection statuses. Review requires explicit `acceptLimitedCoverage: true`; whole-answer findings still require replication or extension. Status remains incomplete. Only the stored accepted flag can authorize generation, and coverage warnings enter the authoritative model context and new plan constraints. Missing/failed AI, all-unclear evidence, stale checks and forged client flags cannot approve generation.
